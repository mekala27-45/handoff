# Model improvement experiment v4

The owner requested another agent-quality round after Handoff v0.2.0. The published v3 operating point remains frozen at configuration 03f2ace4ad3e2215451c41a30ee56c8b1bcd31e6fff88536cc2aeac4135bfd41. Its recorded development score is 8/16 and its fresh held-out score is 2/16, including two validator-rejected incorrect proposals and twelve missing proposals. The original v2 CPU score of 0/16 and every prior failure remain separate records.

The primary v4 hypothesis is that a larger verified open model can complete the bounded tool protocol and choose policy-supported actions more reliably. A short model-catalog digest is insufficient for a lock. The initial registration left model identity unset until the official registry manifest bytes and full digest were captured and verified. That step is now complete for `qwen3:4b-q4_K_M`; the retained registry bytes and actual pull metadata establish the full lock. A short catalog digest or unverified placeholder must not substitute for that identity check. The existing v2 model lock must not be overwritten.

V4 uses a separate agent implementation and new harness, configuration and runner files. The v3 agent and every source file named by its frozen configuration remain byte-for-byte unchanged after LF normalization. The authority boundary also remains unchanged: three scoped proposal tools, observed snapshots, retrieved citations and the existing validator. The model chooses the query, action and citations; code never inserts an evaluator answer. No approval, execution, payment or messaging capability is added. Evaluator truth stays outside agent and application imports.

Development reuses the sixteen preregistered v3 development IDs, with two cases from each of eight families. An initial diagnostic pilot uses damage, identity, duplicate and delay cases already inside that development set. The pilot only checks CPU execution and tool mechanics. It cannot satisfy freeze or establish general quality. All sixteen development cases must be restored and attempted before a candidate can advance.

The acceptance bar is registered in JSON: at least fourteen correct proposals out of the full development sixteen, zero accepted incorrect action/amount/required evidence, zero model-case approvals, review records or effects, complete terminal records and independent SQL observations, calibrated authority counts, and a verified model/CPU lock. Missing outputs, invalid proposals and timeouts remain failures in the full denominator. Any budget or protocol change must be declared before the matching development run and frozen before held-out inference.

The v4 held-out subset is selected from registration metadata only. Of eighty registered held-out cases, the original model subset and v3 subset exclude thirty-two distinct cases. The remaining forty-eight contain six per family. Seed handoff-v4-balanced16-v1 ranks SHA-256 of seed, split, family and fixture ID separated by NUL bytes; ordinal tie-breaking selects two per family. The sixteen sorted IDs have digest 5ba684b155ff675e92e0a713f9c454191e607831b21964aa1fd45b55834c499b. No evaluator truth or model outcomes were consulted for this selection.

The reserved held-out set must run once after the operating point and scope are committed and frozen. Its results must not drive further changes to that operating point or retries counted as new evidence. A reproduction is a repeated run. This subset shares the existing held-out family template lineages, so it is not a new-template test and it is not a paired before/after comparison with v2 or v3.

Actual CPU placement, model digest, runtime versions, hardware, source hashes, effective tool inventory, admission diagnostics and stored SQL proposals must accompany each measured run. Keep infrastructure failures distinct from runs that actually attempted model cases. Preserve original export manifests and bytes. A successful runner exit is infrastructure evidence, not proposal correctness. No model proposal is approved or executed during evaluation, so effect safety is not measured.

The pure recorded-run verifier binds actual SQL proposal IDs, amounts, references, observed version snapshots and validation reasons to the original trace and independent supplied truth. Proposal SELECT completeness is separate from authority-query completeness: either unknown condition blocks freeze and release even when fourteen other cases are correct. A correct-looking metric or successful model runner is not a substitute for these observations.
